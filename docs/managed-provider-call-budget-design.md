# 受管设备连接器：调用预算与启用条件

状态（2026-10-20）：核心及准备、分发、设备观察接合已合入并提交到 `dev`，隔离候选及共享候选各自 62 类、1,576 项完整领域回归通过。本地回归不证明真实网络物理退出或商用 EMM 就绪。本文定义共用实现边界，默认关闭配置保持；下文保留各接合阶段历史，当前交付见[阶段交付](managed-phase-delivery-20261020.md)。

## 1. 实现选择

复用项目已有 Spring Framework 的 `ThreadPoolTaskExecutor`，为受管连接器配置独立执行器。显式固定最大线程数和同等大小的有界交接队列；全部占满时拒绝本次外部调用，由已有持久请求账本负责有界恢复。内存队列只承担本轮调用交接，等待计入当前预算，不承担持久重试，也避免默认公共执行器影响管理 API。

依据：[Spring 6.2 执行器契约](https://docs.spring.io/spring-framework/docs/6.2.x/javadoc-api/org/springframework/scheduling/concurrent/ThreadPoolTaskExecutor.html)提供线程及队列配置和运行指标，默认最大线程数、队列容量并非本产品需要的容量限制。两者均须显式设置。

预算及状态校验属于本业务的薄适配层；线程池、Future、网络客户端、指标采集复用现有框架。暂不为了超时增加另一套异步框架、自动重试组件或通用工作流引擎。

内部调用使用显式预算对象：由一轮准备或分发入口创建，多个读取/核对操作接收同一对象。预算绑定创建它的执行器，不能跨执行器转用；不使用可被嵌套调用意外重置的全局计时器。网络操作只在专用线程执行，参数与权限仍由业务服务核验。

## 2. 四种期限分别处理

| 期限 | 来源 | 使用方式 |
| --- | --- | --- |
| 管理员授权截止 | 发布受理时持久化的绝对时间 | 不因交接、重新准备或服务重启延长 |
| 当前处理租约截止 | 数据库领取时生成 | 旧工作器失效后不能提交结果 |
| 当前设备及应用证据截止 | 本次资格核验结果 | 每个远程动作前重读；排队不能复用过期证据 |
| 本次调用预算 | 受控配置及当前剩余余量 | 单调时钟计时，覆盖提交、等待、解码和结果返回 |

一次操作的可用时间不能超过上述相关期限的最小剩余值。数据库资格查询、外部调用及提交各预留预算，不能把全部租约用在网络等待上。准备中的三次读取共用同一轮预算，不能每读一次重新获得完整时长。分配前核对、再次准备及分配也共用该动作的预算。

绝对授权及证据期限仍由既有服务端/数据库规则复核；单调时钟用于单次耗时计算，不能用进程内时钟值代替持久租约。系统时间调整、排队、重启和线程调度延迟均须纳入验证。

## 3. 超时与线程资源

调用者等待期限到达即停止接受结果，并请求取消。取消只是中断尝试；不能据 `Future.isDone()`、`cancel(true)` 返回值或调用者已返回，认定底层网络和线程已经结束。[Java 17 Future 契约](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/Future.html)

执行器的实际工作线程未退出时仍占用原容量，不创建替代池或不断补线程。提供方忽略中断时，容量逐步耗尽后拒绝新增调用，保持可观测故障，不无限消耗内存。迟到读取不得交接；迟到写入不得补造成功或再次写入，仍通过既有 UNKNOWN 状态与租约核对处理。

连接器接入还必须单独证明连接、读取、连接池获取、响应体大小、重定向、凭证刷新及资源关闭行为。只有调用者超时而连接器资源无限滞留，不能通过启用检查。线程隔离是服务保护手段，不构成已具备端到端网络取消能力的声明。

## 4. 事务与权限

- 提交连接器调用前禁止存在外层数据库事务；工作线程也不得携带调用线程的事务上下文。
- 只传入本次已核验的内部目标与冻结文档，不传入原始管理员令牌、HTTP 请求或可变页面状态。
- 不复制线程本地安全上下文来替代当前数据库权限检查；返回后继续复核租约、管理员关系、设备注册和绑定版本。
- 写入前 UNKNOWN 检查点必须已提交。容量拒绝或超时不得绕过检查点，也不得触发透明自动重试。
- 诊断只记录固定阶段、错误类型、关联 ID 和耗时，不记录凭证、提供方正文或完整策略。

## 5. 故障结果与产品呈现

| 场景 | 后端处理 | 管理端说明 |
| --- | --- | --- |
| 池满、读取超时 | 按原请求剩余期限和次数限制重试 | 连接服务繁忙，等待再次确认 |
| 资格或内容变化 | 结束当前请求，保留原因 | 设备或规则状态已变化，请重新检查 |
| 写入后无法确认 | 保留 UNKNOWN，进入只读核对/正式复核 | 正在确认下发结果；不提供重复发送 |
| 调用忽略中断 | 计入真实占用，触发容量告警 | 不把管理员页面无限阻塞 |
| 原授权到期 | 按现有状态机结束/复核 | 本次执行期限已到；不自动续期 |

## 6. 启用一致性

启用准备受理前必须确认：持久事件与扫描恢复、准备执行器、写入消费、设备观察、正式人工处置、连接器调用预算及当前提供方能力已完整配置。不能只检查某个 `enabled=true`。非法组合在启动配置校验中明确失败；动态提供方失效时暂停新增受理，保留本地查询、取消和到期收敛能力。

专用执行器、调度器与事件消费者须有明确名称和生命周期。服务关闭先拒绝新任务，再在有界时长内停止；数据库和凭证资源的关闭顺序需要真实进程验证。进程被强制终止后由持久状态恢复，不能依赖 JVM 内的回调补交。

### 配置接合的实施清单（待实现）

当前隔离来源的配置分别控制不同组件，不能把单一开关当作整条链路可用。以下为下一阶段约束，尚不是已经生效的启动校验。

| 当前配置 | 管理对象 | 拟校验的关系 |
| --- | --- | --- |
| `manager.emm.execution.admission.enabled` | 新发布的持久受理 | 仅在准备、恢复、写入、观察、正式人工处置及连接器能力全部就绪时允许开启 |
| `manager.emm.execution.preparation.enabled` | 提交后的准备事件监听 | 必须绑定专用有界执行器，且持久扫描恢复开启 |
| `manager.emm.execution.preparation.recovery.enabled` | 准备请求恢复扫描 | 与准备服务配套，重投不重复领取有效租约 |
| `manager.emm.execution.dispatch.enabled` | 策略写入、分配消费 | 观察与不确定结果处置路径必须已具备；关闭新受理不自动停止存量恢复 |
| `manager.emm.execution.device-recovery.enabled` | 精确版本的设备回执观察 | 可以在新受理关闭时继续处理存量任务 |
| `manager.emm.provider-calls.*` | 提供方调用线程、队列和预算 | 独立于事件执行器；不能共用同一个受限线程池再同步等待自身 |

事件线程池只接收轻量请求标识，任务执行时才领取租约；队列满时拒绝，不能在发布事务的线程执行提供方操作。持久请求与扫描器承担恢复，进程内队列不承担持久性保证。事件完成不能代替请求终态，扫描回放仍须经过同一工作器。

各阶段提交预留必须小于对应租约；读取预算取“配置上限”和“租约扣除预留后的剩余量”较小值。允许租约缩短实际预算，拒绝根本没有正余量的静态配置。准备租约与执行租约分别校验；数据库时钟与进程时钟偏差需要运行指标和部署时间同步约束，不能用自动延长租约掩盖。

启动时校验稳定的配置和组件依赖，不为检查就绪而发起策略写入；运行期间提供方失效则拒绝新增受理。运维可区分“允许新请求”“存量任务可恢复”“连接器暂不可用”，避免用一个总开关使所有查询和恢复一起失效。真实人工处置尚未实现时，生产受理继续关闭。

## 7. 必须取得的验证证据

1. 实际线程池验证线程和队列上限、全部占满后拒绝、容量释放和顺序调用交接；不只断言配置值。排队期间到期的操作不得执行。
2. 阻塞读取、忽略中断和迟到返回分别验证；检查真实活跃线程数，不以 Future 完成代替。
3. 多次读取共享预算；第一次消耗的时间不能在第二次重置；已经到期时不得调用提供方。
4. 调用者中断标记保留；错误内容及堆栈因果链不泄露提供方秘密。
5. 外层事务拒绝、后台线程无事务、返回后撤权/取消/接管均拒收。
6. 写操作超时或取消后只有一次提供方调用；后续消费者不盲重发，独立设备证据仍为生效依据。
7. 本地可控 HTTP 服务验证连接/响应/大响应/异常关闭/凭证刷新路径；外部合作方另提供真实传输验证。
8. 真实服务重启、MySQL/OceanBase 锁与事务、连接器失效和批量广播容量独立验收。

以上按完整业务链列出验收要求，核心组件已取得的局部证据见第 8 节，整条链路尚未验收。现有 H2 和提供方替身测试不能替代第 7、8 项，也不能证明 Android 真机或合作方资质已通过。

### 执行只读核验的接口契约

资源归属服务和执行准备服务均提供显式预算入口，供上层分发复用。一次资源归属核验的顺序为：预算检查 → 当前任务准备 → 预算检查 → 提供方资源归属读取 → 当前任务检查 → 再次准备 → 当前任务、证据有效期与预算检查。两个准备步骤必须接收同一个预算对象；已有身份读取、配置读取和编译检查继续消耗该对象的剩余时间。

直接调用入口只创建一次预算，上限为已配置的提供方预算与租约剩余时间的较小值；任务原始有效期仍由持久账本检查。分发调用必须选择显式预算入口，不能通过反复调用直接入口重新获得完整时间。任何预算都不取代租约令牌、当前绑定、发布版本或资源归属证据。

| 失败位置 | 服务行为 | 是否改变执行任务 |
| --- | --- | --- |
| 准备开始前或结束后预算失效 | 拒绝准备结果，返回固定错误码 | 本层不改变任务 |
| 资源读取超时、拒绝或提供方异常 | 返回固定服务不可用错误，不带外部响应和异常链 | 本层不改变任务 |
| 两次准备之间发生取消或权限变化 | 继续沿用已有当前任务与权限错误 | 本层不改变任务 |
| 上层写入动作收到以上失败 | 由分发层根据持久状态处理，禁止自动重发不确定写入 | 按账本状态机处理 |

新增 14 项检查先实测为 11 处预算缺口及 3 项既有控制通过，见[缺口记录](evidence/managed-execution-read-budget-red-20261018.json)。实现接合后，独占窗口内 536 源编译通过，完整 54 套、1,413 项回归全部通过；格式化、编译、测试分别耗时 1.4、31.6、103.6 秒。资源门槛、源/产物摘要、耗时与自然进程退出检查通过，见[候选验证记录](evidence/managed-execution-read-budget-candidate-20261018.json)。

这些证据覆盖执行只读核验接合，尚不覆盖分发、分配和设备观察整轮预算，也不证明真实提供方网络已物理退出。共享源码尚未移植，生产开关没有开启。

错误语义约定：执行准备的预算失效使用 `EXECUTION_PREPARATION_PROVIDER_UNAVAILABLE`，资源读取失效继续使用 `MANAGED_RESOURCE_PROVIDER_UNAVAILABLE`。两者不携带外部响应、设备资源名或异常因果链。管理端应先读取任务的持久状态，再决定显示“准备未完成”“等待确认”或“需人工处理”；不能仅凭服务不可用错误断言写入未发生，也不能提供绕过账本的新请求重发按钮。

### 分发与排队后的当前权限核验

分发层从剩余租约扣除本地提交预留（默认 10 秒），只建立一份预算，贯穿准备、资源归属读取、内容检查、写入及分配。调用方提交前、提供方工作线程开始写入前、返回后均检查当前任务和权限；队列等待不会冻结管理员授权。工作线程真正调用写入前，复用原有绑定、发布版本、连接器、证据期限核验。

持久 UNKNOWN 检查点仍先于远程写入。超时、排队期间撤权或迟到响应均不能把它回退成可重发状态。最终本地提交使用预留时间，并继续受原租约与事务限制；这不代表数据库驱动可被预算检查强制终止。

新增 16 项预算检查、6 项排队检查先取得实际失败证据；修复及测试同步调整后，完整 56 套、1,435 项通过，见[分发候选证据](evidence/managed-execution-dispatch-budget-candidate-20261018.json)。中间一次测试同步失败独立保留，未改写成通过。设备观察预算仍未接合；实际网络退出、凭证刷新、人工处置、配置完整性和真实数据库验收尚未完成，生产开关保持关闭。

### 准备事件的独立容量与恢复

已验证的隔离候选为准备事件提供独立 Spring `ThreadPoolTaskExecutor`，通过 `@Async("managedPreparationExecutor")` 明确选择。提供方调用继续使用既有独立执行器，避免准备线程等待自己所在的提供方队列；通用通知池饱和时，准备唤醒仍能执行。该候选尚未集成到当前服务。

| 设置 | 默认值 | 启用时边界 |
| --- | ---: | --- |
| `manager.emm.execution.preparation.executor.workers` | 2 | 1–16，核心与最大线程数相等 |
| `manager.emm.execution.preparation.executor.queue-capacity` | 64 | 1–1,024，仅内存唤醒引用 |
| 拒绝策略 | AbortPolicy | 禁止 CallerRuns；不在发布请求线程临时执行准备 |
| 关闭 | 拒绝新任务，取消未开始的唤醒 | 持久请求与未完成事件保留，下次由恢复流程处理 |

使用 Spring 6.2 已提供的容量、拒绝与关闭接口；队列容量不会自动成为线程数上限，必须同时设置固定线程数。关闭行为通过实际 Spring 上下文测试，不能只检查配置字段。[Spring 线程池文档](https://docs.spring.io/spring-framework/docs/6.2.x/javadoc-api/org/springframework/scheduling/concurrent/ThreadPoolTaskExecutor.html)

Ruling：专用队列承担唤醒与资源隔离，不替代数据库工作状态。队列满导致提交后的唤醒失败时，已提交的发布、准备请求和未完成事件继续存在；不能把 HTTP 异常解释为发布未发生。恢复重投和定时请求扫描仍通过原工作器领取租约，不能在入队时提前领取，也不能绕过当前权限或重复执行不确定写入。

上述线程数仅限制事件唤醒通道。现有定时扫描仍按有界批次顺序调用工作器，额外占用调度执行线程；提供方调用总容量继续由 `ManagedProviderCalls` 限制。不能把事件池大小表述为全服务的并发上限。定时任务之间的调度隔离、真实进程重启和分布式容量仍需后续联合验收。
