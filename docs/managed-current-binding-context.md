# 受管应用核验前的当前绑定检查

更新：2026-10-16。状态：当前绑定短事务读取已实现，75 项定向检查通过，尚未部署到运行服务。此步骤属于逐设备应用证据接入，不表示系统策略已经可以执行。

## 用户目标与边界

管理员仍通过“选择设备 → 预览影响 → 确认发布”完成操作。服务端在准备读取提供方应用报告时，重新确认当前成员权限、设备注册及受管绑定；调用完成后还要再次读取并比较，避免撤销或重新注册期间接受旧结果。

`requireVerifiedContext` 是 managedandroid 内部的短事务入口，不提供新的 HTTP 接口，不允许客户端构造受信快照，也不向普通界面展示提供方资源、注册密钥指纹或内部代次。

## 读取约束

1. 先锁定并检查当前租户成员，只有机构所有者和机构管理员可进入；记录成员权限版本。JWT 有效不代表已撤销的成员关系仍有效。
2. 沿用绑定工作流的授权和领域锁顺序：成员 → 企业关联 → 学生及设备 → 合同容量 → 绑定。事务内不调用提供方。
3. 核对受管注册已验证、企业及提供方仍对应、学生未归档、设备及本次注册有效、密钥指纹一致、当前机构合同仍有资格。
4. 绑定必须为当前版本的 `VERIFIED`，挑战已消费，独占设备及受管注册槽位一致；核验时间必须存在，且不早于请求创建、不晚于当前时间。
5. 当前接入只接受已有绑定流程支持的 `DEVICE_OWNER`；不能凭此扩展到工作资料或所有电视机型。
6. 已完成绑定不受原挑战截止时间影响。挑战期限控制一次性证明，后续绑定有效性由当前授权、注册、撤销状态及信任配置共同决定。

## 发布签名信任修订

成功消费绑定证明时，将当时的代理包名和全部受信签名集合生成稳定摘要，写入 `managed_agent_bindings.agent_trust_revision`。集合先排序、去除配置空白，使用现有 SHA-256 工具；不保存新的原始证明或设备影像。

读取当前绑定时，必须与当前部署的信任修订一致。旧记录缺少修订或信任配置变化均要求重新绑定；不能把当前摘要回填到历史记录并声称已重新验证。单纯调整签名排列顺序不改变修订；增加、删除签名或更换代理包名会改变修订。

V1 仅维护未发布的初始化基线，新增可空字段用于明确识别旧/缺失证据，并同步数据保留目录。只在隔离空库验证，不原地修改现有运行库。后续生产升级须走正式向前迁移和重新核验安排。

需要重新绑定时，管理员先以近期认证撤销旧本地关联，再发起新的绑定证明。该操作不退出提供方设备管理、不释放原受管注册名额，也不能直接回填信任摘要。

## 快照与后续消费

内部不可变快照包含租户、操作者及权限版本、学生、设备及注册、密钥指纹、绑定及修订、受管注册及修订、提供方、企业关联及修订、提供方设备、管理模式、绑定核验时间及代理信任修订。诊断字符串脱敏；不包含挑战、签名证明、公钥或注册令牌。

该快照只证明事务读取时本地绑定上下文有效。它不能证明目标应用已安装、目标应用签名正确、用户空间已映射、系统能力已支持或策略已应用。后续应用报告流程还需：

- 在事务外读取提供方报告并校验来源；
- 在新的短事务中重新检查当前绑定、应用定义及报告时间；
- 将证据按设备、注册、绑定、应用身份及连接器修订保存；
- 预览、发布和执行前重新校验有效期与撤销状态。

不能缓存这份快照后跳过当前授权，也不能将它本身作为长期执行凭证。读取入口不写审计成功事件或刷新绑定有效期；证据接受、拒绝及后续执行由对应工作流记录。

## 本轮验证结果

真实 Spring、MVC、H2 MySQL 模式和事务验证；沿用已有设备凭证及租户权限实现。提供方、机构准入和合同容量仍是明确测试夹具，不能代表生产 EMM 或真实合同验收。

51 项绑定检查通过，包含 18 项原有回归及 33 项新增检查；覆盖当前绑定正向读取、挑战截止后正常读取、权限版本、角色和跨租户隔离、撤销、设备及学生状态变化、提供方/企业/受管注册修订变化、签名信任撤销、版本冲突及账本不变性。另有 24 项受管绑定数据清理回归通过，确认保留目录匹配新字段。

设备重新注册使用新的设备及注册 ID；绑定表的复合外键禁止保留旧引用的同时直接改写原设备注册 ID。本轮没有通过关闭外键制造不可达状态，也没有声称覆盖真实设备重新注册联调。

RED 候选 `managed-current-binding-red-20261016-r1` 基于 `94079e7` 固定 438 个文件；1 项新正向场景因默认拒绝发生预期断言失败，0 错误、0 跳过，Maven 退出 1，49.6 秒。随后 GREEN r1 的 75 项中有 2 项失败：测试误将成员初始权限版本写为 1，而 V1 的定义为 0；实现返回值正确。旧候选及失败结果已保留。

按实际 DDL 修正版本断言为 0 → 1，并让撤销夹具使用时间戳类型后，GREEN r2 在新的隔离候选中执行：**75 项通过，0 失败、0 错误、0 跳过**，Maven 退出 0，50.3 秒，438 个源码摘要未变化。两个共享资源在候选中只包含本轮新增字段，不包含其他任务的未提交功能。

本轮没有重跑全后端、MySQL/OceanBase、真实提供方或 Android/TV；这些检查不能由 H2 回归替代。运行服务和已有数据库保持原版本。实际结果、命令、文件及日志摘要见[验收证据](evidence/managed-current-binding-context-20261016.json)。

## 新增拒绝原因

| 错误码 | 原因及下一步 |
| --- | --- |
| `MANAGED_BINDING_NOT_VERIFIED` | 尚未验证或已撤销；完成新的绑定流程 |
| `MANAGED_BINDING_PROVIDER_CHANGED` | 当前连接器与绑定提供方不一致；管理员检查接入配置 |
| `MANAGED_BINDING_MODE_UNSUPPORTED` | 当前绑定读取尚不支持此管理模式；不能推定拥有设备所有者能力 |
| `MANAGED_BINDING_VERIFICATION_INVALID` | 核验时间、一次性挑战消费或独占槽位不一致；先检查记录并重新绑定 |
| `MANAGED_BINDING_RELEASE_TRUST_CHANGED` | 缺少历史信任修订或签名信任配置已变化；重新核验绑定 |

原有权限、版本冲突、合同、注册及企业变更错误继续复用既有语义。新错误目前只用于内部读取入口，后续接入预览时需要对应的可理解文案与恢复入口。
