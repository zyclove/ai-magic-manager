# 受管执行链的启动配置检查

状态（2026-10-20）：检查逻辑已实现，两种候选各自完整领域回归通过，源码已合入并提交到 `dev`；部署仍待完成。生产受管执行保持关闭，当前来源见[阶段交付](managed-phase-delivery-20261020.md)。

## 1. 要解决的问题

管理员发布规则后，服务需要依次完成准备、下发、设备观察和结果记录。仅打开“允许发布”，而没有开启后续处理任务，会使请求进入持久队列后无法继续。本设计在服务启动时发现此类配置错误，并保留停止接收新任务、继续处理存量任务的维护方式。

检查采用项目已有 Spring 生命周期与容器机制，不增加另一套任务队列或调度系统。启动检查只证明本机组件装配完整；提供方准入、网络可用性和设备生效仍有各自的独立判断。

## 2. 配置关系

以下属性均位于 `manager.emm.execution` 下，默认关闭。

| 属性 | 用途 | 启用要求 |
| --- | --- | --- |
| `admission.enabled` | 接收新的受管执行发布 | 准备、准备恢复扫描、分发、设备观察全部开启 |
| `preparation.enabled` | 处理发布后的准备事件 | 准备工作器、监听器、专用执行器及异步处理基础组件存在 |
| `preparation.recovery.enabled` | 扫描遗漏或需要重试的准备请求 | 准备已开启，恢复任务及调度组件存在 |
| `dispatch.enabled` | 消费策略写入与分配任务 | 设备观察已开启，分发任务及调度组件存在 |
| `device-recovery.enabled` | 查询独立设备回执 | 设备观察任务及调度组件存在 |
| `manual-review.enabled` | 允许管理员申请重新核实设备 | 设备观察已开启；提交时还要检查当前服务、身份、版本和任务条件 |

标志与实际组件同时核对。消费者按类型要求唯一；准备执行器按固定名称及类型核对，不能用一个无关对象满足配置。默认全部关闭时，不初始化延迟加载的工作器，也不发起外部提供方请求。

### 常用运行方式

| 方式 | 新发布 | 准备及恢复 | 分发 | 设备观察 | 用途 |
| --- | --- | --- | --- | --- | --- |
| 普通配置管理 | 关 | 关 | 关 | 关 | 维护规则配置，不声称系统已执行 |
| 完整执行 | 开 | 开 | 开 | 开 | 在满足提供方及设备准入后处理新发布 |
| 存量处理 | 关 | 开 | 开 | 开 | 维护期间停止新受理，继续处理已有任务 |
| 只读观察 | 关 | 关 | 关 | 开 | 继续核实设备现状，不新增策略写入 |

人工复核可随设备观察单独启用，但不能延长原任务授权、恢复已取消任务或手动认定设备已生效。关闭新发布不会删除队列、清除设备占位或重置任务期限。

准备与恢复也可单独运行以处理准备阶段的存量数据；该方式可能继续生成等待分发的任务，不能显示为“全部任务已处理”。完整排空应使用上表“存量处理”方式并检查持久任务状态。

## 3. 多实例与运行时边界

当前阶段采用完整模块化应用副本，每个接收受管发布的副本都具备完整执行组件，跨副本仍由持久状态、版本和租约协调。多个副本存在同类工作器不违反“本机按类型唯一”的检查。

单独部署 API 服务、把所有工作器放在其他主机的方式，需要进一步实现共享的工作器就绪协议。不能通过本机布尔配置推断远端工作器存在；当前草稿不会把缺少本地消费者的 API 节点判为完整执行节点。这不影响完整副本的水平扩展方案。

启动成功不证明后续持续健康。提供方暂不可用时，新受理仍由现有服务检查拒绝，存量任务继续遵循有界重试、期限和未知结果处理规则。一般 HTTP 健康状态不能代替“受管执行可用”，更不能代替设备生效回执。

## 4. 错误处理与实施

候选实现位于 `ManagedExecutionPipelineConfiguration`，使用 `SmartInitializingSingleton` 在普通组件实例化后检查装配。非法开关组合在启动过程中被拒绝，不等到管理员发布后才发现。错误说明包含固定属性名或组件名；此检查器的布尔转换错误不附带原始环境值。

启用分发或设备观察时，同时检查其租约与提交预留：租约必须为正，预留必须非负且小于租约，从而保留实际提供方调用时间。关闭的阶段不因其未使用的预算配置阻止只读观察节点启动。检查不以延长租约掩盖无效配置，配置值不会出现在公开错误中。

不通过关闭权限校验、替换数据库事实或调用真实提供方来使启动检查通过。现有事件仓储验证继续使用真实 Spring、JDBC 和事件仓库，并明确把后续调度任务作为惰性行为的测试替身；不会从该验证中移除生产检查器。

合入时分别核对可提交来源和共享工作区来源：已提交的历史发布模式恢复必须保留；家庭业务尚在工作区的再次认证方法与数据库扩展也必须保留，但不能让独立提交依赖尚未提交的实现。

## 5. 实际验证与交付条件

2026-10-19，修复前冻结来源共 546 份。编译实际退出 0，用时 62.3 秒；24 项启动组合检查中，17 项复现“错误配置仍成功启动”，7 项正常场景通过，0 初始化错误、0 跳过，测试退出 1，用时 13.1 秒。逐项失败原因、来源和回执摘要见[实际缺口记录](evidence/managed-execution-pipeline-readiness-red-20261019.json)。
