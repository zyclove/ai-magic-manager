# 1.0.0 删除账本启动保护

承接主体删除契约及已提交的独立账本。本阶段实现启动前保护与标准部署接线，正式删除继续关闭；不是历史版本迁移。

## 设计与完成条件

1. 使用 Spring `SmartInitializingSingleton` 在上下文完成刷新、服务进入就绪和定时任务开始之前检查账本。配置了账本 URL 或声明要求账本时，缺失、失联、未知身份、损坏和非零接受序号均阻止启动，异常只包含稳定错误码。
2. 当前尚无域处理器和已应用业务水位，因此任何已接受记录都必须进入人工恢复处理，不能把读到尾部当作完成，更不能自动清空账本。此阶段只允许已验证空账本启动。
3. 未配置账本的源码开发环境保持现有行为，删除执行仍关闭；Compose 和 Helm 的 API/worker 标准部署强制声明需要账本，并要求独立配置。未来接受删除必须同时要求完整恢复协调与运行期隔离，不能据此启动保护单独开放接受接口。
4. Compose 使用独立账本数据库、账号、凭据和卷；生成全新部署目录时生成账本 ID。新增显式离线初始化步骤，普通启动不得自动初始化或重建账本。独立卷不等于跨基础设施故障域独立。
5. Helm 要求独立账本 URL、用户名、固定 ID 与已有 Secret，启动 API 和 worker 时都执行检查；不向 chart 写入明文密码。
6. 验证先覆盖缺失保护的失败用例，再检查生命周期次序、缺失/失联/待处理记录、空账本启动、标准部署配置和发布包实际启动行为。保留测试范围与限制；只做一次最终阶段复核。

## 决策与边界

- Ruling：使用失败即停止启动，避免恢复状态未判定时先接收请求或启动后台任务；尚无恢复协调器时不提供自动解除保护入口。
- Ruling：检查配置开关是源码开发与标准交付的边界，不是允许正式删除的开关。标准交付强制要求账本；源码开发未配置账本时仍不能执行删除。
- Ruling：仅证明启动时保护。已运行实例的跨节点实时隔离、域处理器、业务完成水位及真实旧备份恢复后再删除仍是后续必需项。

## 已验证的实现与限制

- 启动保护的首次失败验证为 5 项中的 4 项失败；实现后 5 项通过。额外覆盖全局延迟初始化后共 6 项；Spring Boot 已将 `SmartInitializingSingleton` 排除出全局延迟初始化，因此无需另加生产配置绕过。
- 部署工具 8 项及 Helm 渲染 3 项通过。真实 MySQL 应用集成 2 项通过，使用独立临时库。
- 独立 Compose 项目验证了空账本允许后端健康启动；一条合成接受记录或缺少账本配置均使进程在就绪前失败；运行账号的 DELETE 被数据库拒绝。
- 首次容器初始化暴露了 MySQL 镜像对数据库名下划线的授权转义：按原始数据库名撤销权限不能匹配该授权。改为先撤销专用账号全部权限，再授予两张表的最小权限，在另一个全新项目上完成初始化。失败尝试没有写入成功回执。
- 重复初始化被拒绝，凭据、账本身份与初始化回执保持不变。
- 一次独立最终复核覆盖 14 个固定哈希的源文件，无发现；不进行第二次复核。
- 最新商业模块联合回归曾有 4 项因测试未启用发行方开关而失败；该失败单独留档，由该模块修正测试夹具后再验收，不降低发行方校验。

Final: Ruling: 跨节点运行期隔离、已应用水位、域删除与真实恢复再删除仍未完成 — 正式删除保持关闭；误将启动保护当成删除功能完成会导致恢复后的数据重新出现，因此禁止据此开放接受接口。

Final: Ruling: Compose 的独立卷仅证明本机逻辑隔离；Helm 仅验证渲染 — 真实 Kubernetes 故障域、Linux 凭据挂载及生产恢复需独立验收，否则可能高估部署可靠性。
