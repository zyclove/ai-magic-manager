# 独立删除账本与恢复检查（1.0.0）

承接 data-erasure-contract.md 的独立持久记录与恢复要求。上一阶段短期准备已经完成并提交 9c88b5c，正式删除仍禁止执行。本阶段不修改其他线程正在维护的业务 V1 和存储清单；账本位于独立数据库，使用单独初始化资源。

## 实现与验证顺序

1. 独立 JDBC 账本：显式离线建库，运行服务只连接既有账本，检查账本身份、版本、表列及与业务库分离；不自动创建或修复缺失账本。
2. 接受记录：租户/主体不透明 ID、设备不可变注册范围、操作者摘要、政策/范围摘要、请求 ID、接受时间。拒绝重复目标、无界内容与未知格式；不保存姓名、邮箱、理由、凭据或导出正文。
3. 通过账本头行锁分配连续序号，唯一请求 ID 绑定规范化请求摘要。重试返回原记录，冲突拒绝。独立事务提交不随业务事务回滚；没有公开 HTTP 写入入口，未来提交服务必须先完成权限与确认。
4. 连续 SHA-256 链验证记录意外损坏、缺失或错序；它不证明拥有数据库写权限者没有重写整个账本。初始化账本 ID 由部署持久保管并在运行时固定，不能随业务备份回退。
5. 恢复检查绑定账本 ID、业务已处理序号与摘要；未知身份、账本落后、断链、缺失记录或访问失败均拒绝就绪。未处理记录按有界批次返回。只有所有域处理器和外部回执完成后，未来协调器才允许推进业务水位。
6. 删除前检查接入账本可用性，缺少配置或有未协调记录时明确返回阻断原因。正式删除执行继续关闭；当前阶段不能声称应用启动/所有访问和后台任务已受恢复闸门保护。
7. H2 和独立 MySQL 验证：初始化/重复初始化拒绝、独立事务、并发幂等、冲突、损坏、空洞、失联、旧业务水位追赶。后续必须接入全局恢复维护状态、域隔离和真实旧备份恢复演练，才能启用正式删除。

## 决策与边界

- Ruling：使用已有 JDBC/事务工具和独立 MySQL 账本，不引入第二类数据库或消息系统；数据库、访问凭据、备份和恢复范围独立配置。
- Ruling：正常运行从不自动重建丢失账本。离线初始化只面向明确的新账本，已有对象时拒绝覆盖。
- Ruling：先交付真实持久化与恢复判定并接入删除前检查，再把域隔离/恢复协调器接到启动及所有访问入口；未完成链路前不接受任何用户删除操作。不能把判定组件验收当成完整恢复防护验收。

## 新环境初始化与运行

账本是 1.0.0 新环境的独立存储，不属于业务 Flyway 初始化位置，不提供历史版本升级脚本。先创建空的 MySQL 数据库，使用仅针对该库的初始化凭据。通过环境变量提供 `ERASURE_LEDGER_URL`、`ERASURE_LEDGER_USERNAME`、`ERASURE_LEDGER_PASSWORD`、`ERASURE_LEDGER_ID`；ID 使用小写 UUID，并与部署配置一起持久保存，不能在业务恢复时重新生成。命令行参数不得包含密码。

使用发布包执行一次显式初始化：

```text
java -Dloader.main=com.aimanager.retention.internal.ErasureLedgerBootstrap -cp manager-backend-1.0.0.jar org.springframework.boot.loader.launch.PropertiesLauncher initialize-new-ledger
```

实际 JAR 文件名以构建产物为准。已有表或视图时拒绝初始化；初始化中断后由运维检查，服务不会清空、修复或重新创建账本。应用启动时使用相同四个配置项，但换成受限运行账号：账本头只需 SELECT/UPDATE，条目只需 SELECT/INSERT，不授予 DELETE、DDL 或业务库访问权限。业务账号不得访问账本库。元数据必须对各自账号可见，以便检查表与列。

生产部署还必须安排独立的备份和恢复权限、保留策略与故障域。本地两个 MySQL 数据库的测试只证明逻辑与事务隔离，不能证明跨基础设施独立。摘要链可以发现意外缺失与损坏，不能阻止高权限攻击者重写全链。

两端数据库名称必须非空，且忽略大小写后不同；即使位于不同服务器，同名库也会被保守拒绝。该限制避免受限账号隐藏表后绕过同库检查。账本两表固定为 InnoDB，运行时同时检查实体表和存储引擎；不能通过服务器默认引擎配置改成 MyISAM。

每个请求最多含 1000 个设备注册范围，序列化内容最多 262144 字节；每批最多读取 100 条。超过上限直接拒绝，不截断。正式接受大规模删除前必须完成范围分批设计。`Page.nextRead` 和 `endOfSnapshot` 仅描述读取进度，不能当作删除完成、外部回执完成或恢复流量的许可。`head()` 只检查头及尾记录；完整历史链通过有界读取验证。

当前未配置账本时普通应用仍可运行，删除前检查返回 `ERASURE_LEDGER_NOT_CONFIGURED`；已有记录统一返回 `ERASURE_LEDGER_RECONCILIATION_REQUIRED`。删除执行始终关闭。账本没有公开写入接口，不能用内部 append 的测试通过代替用户确认、所有域隔离、清理和恢复闸门验收。

## 一次阶段复核与修复

执行一次独立只读复核，初始 10 个源码/测试/SQL 文件摘要全部匹配。复核发现 3 项需要修复的问题；一次修复中增加 4 个 MySQL 回归，先得到 4 项预期失败、0 项错误，再得到全部 14 项存储测试通过：

- P1：默认 MyISAM 可创建非事务表。初始化显式指定 InnoDB，运行时检查两张实体表的引擎；测试覆盖默认引擎改变和运行表改为 MyISAM 两种情况。
- P2：表级授权隐藏账本表可能绕过同库检查。增加非空、忽略大小写的 catalog 名称分离检查；受限元数据视图模拟用例先失败后通过。
- P2：合法 JSON 后追加第二个根值被解析器忽略。启用 `FAIL_ON_TRAILING_TOKENS`；尾随内容用例先失败后通过。

Ruling：接受上述三项发现并完成同一轮修复，不再启动第二次复核。复核未评判的用户删除入口、域处理器、业务已应用水位、全局维护闸门、独立基础设施备份和真实旧备份恢复演练均保留为后续交付项；高权限重写全链继续属于明确不保证的范围。其他线程的商业与界面变更不在此次账本复核范围。
