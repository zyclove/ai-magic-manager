# 审批通知中心实施计划

## 目标与既有依据

落实完整产品计划 Task 1、5、7、9、10 中的通知与审批工作台，依据功能规格 APR-01 的去重提醒及 SAF-01 的通知与业务事实分离。当前阶段交付站内审批通知完整链路：真实申请状态变更、持久通知、当前权限过滤、未读数量、分页/筛选、个人已读状态和打开当前申请。邮件、短信、移动推送与其他安全告警仍保留在全产品范围内，不把站内功能称为完整 SAF 验收。

使用已有 Spring Boot/Modulith 事件、JDBC/Flyway、Spring Security、Flutter Material/provider。复用现有管理端设计系统；12ui 托管服务此前已出现地区限制及上传审批拒绝，不以重试上传绕过限制。

## 实施决定

- Ruling: 申请状态与精简站内通知同事务持久化，每个申请版本只记录一次 — 使用既有领域事务，避免用户看到无事实依据的提醒或丢失通知 — 数据库写入失败会使该次业务事务整体回滚；后续外部推送失败不得改变已完成的审批。
- Ruling: 站内通知按当前工作空间角色及学生范围投影，儿童/教师只读本人申请 — 与现有审批查询权限保持一致，无须向大量成员同步复制私人理由 — 新加入且有当前权限的管理者可看到保留期内的历史通知，通知正文不复制申请理由、身份或令牌。
- Ruling: 已读状态是个人、单向且幂等的，不改变审批 — 重放保持首次已读时间；批量操作仅覆盖显式选定的当前页，最多 50 项 — 不提供可能吞掉并发新消息的无限“全部已读”。
- Ruling: 通知记录是发生时的状态事实，打开申请重新读取当前状态 — 批准提醒不等于设备已解锁，旧提醒不能恢复已撤回或到期授权 — 页面须清楚区分“当时的提醒”和“当前处理结果”。

## 契约

- `GET /api/v1/tenants/{tenant}/notifications?limit=20&cursor=...&unreadOnly=false`：按发生时间、UUID 倒序，透明游标绑定两个排序字段，最大 50 项。
- `GET /api/v1/tenants/{tenant}/notifications/unread-count`：相同访问过滤，计数最多 1,000，返回 `count` 与 `capped`。
- `PUT /api/v1/tenants/{tenant}/notifications/{id}/read`：仅当前个人的可见通知，单调、原样重试安全，保留首次已读时间。
- `POST /api/v1/tenants/{tenant}/notifications/read`：显式 `ids` 1–50 项，无重复；全部验证通过后同事务标记，跨范围输入不部分成功。
- 当前角色 OWNER/GUARDIAN/ORG_ADMIN 可看范围内管理通知；TEACHER/CHILD 还须匹配本人申请和当前主体授权；AUDITOR 没有此处理入口。每次读取核对数据库成员事实。
- 通知字段只含通知/申请/主体/设备标识、申请版本、状态、发生时间和个人已读时间。无理由、完整 OIDC 主体、邮箱、令牌。
- V21 建表并为存量申请当前版本生成通知；默认保留 30 天（可配置 1–365 天），有界清理同时移除对应已读状态。审计与申请历史不受通知清理影响。
