# 儿童设备临时访问申请实施计划

承接 `79d509c`，实现设备凭证发起申请、成人重新认证审批、设备查询/取消与现有签名窗口接收的业务衔接。沿用 Spring Security、Validation、JDBC/Flyway、持久幂等和既有审批领域；不生成伪造儿童 JWT，不把请求当作解锁。

## 分层和步骤

1. 新增设备专用 `/api/v1/device-api/access-submissions`，含选项、创建、列表、详情和取消。保留既有 `/access-requests` 签名交付协议。服务端从设备凭证绑定推导租户、主体、设备及注册周期；请求只能提供当前基础策略、应用、规则、时长和可选理由。
2. 在既有申请表增加显式 MEMBER/DEVICE 请求人类别，历史行归 MEMBER。设备请求人稳定绑定注册周期，不绑定轮换凭证 ID；成员撤权、本人审批判断和取消必须区分主体类别，避免 OIDC sub 与设备审计名碰撞。
3. 复用唯一申请槽、冷却、幂等、强版本和生命周期；创建按基础策略→主体→设备→凭证→申请锁顺序复核。变更或重试返回当前事实，不重放已过期批准；审批仍仅成人近期 MFA。
4. 增加 Dart 设备申请契约、严格解析和传输，随后接入儿童端表单、待审批/已拒绝/已取消/到期等状态。重试必须沿用原幂等键和原输入；不能离线假创建或提示已解锁。
5. 验证真实 opaque 安全链、HTTP/SQL/事务、凭证轮换、不同主体类别碰撞、跨租户/设备/注册、撤权、版本冲突、重复/冷却、基础变化和历史迁移；客户端补失败/未知结果/身份变化流程及界面验证。
6. 以冻结候选逐阶段验收、精确提交并推送 dev。共享审批文件待协调任务冻结后合并；不纳入其他任务的未验收文件。完整产品目标保持有效，系统执行和后台能力仍另行交付。

## 设计判断

Ruling: 使用专用设备申请主体，而非为设备构造 CHILD 成员 — 设备已具成人确认的注册范围，成员身份应独立于设备 — 类别判断遗漏可能混淆同名主体，因此加入碰撞与生命周期专项回归。

Ruling: 设备申请和签名交付分开路由 — 现有交付列表只含已有批准文档，不能改变为全部待审申请而破坏 SDK — 客户端需明确区分申请事实与收到的签名安排。

Ruling: 先在父提交独立候选实现 — 另一任务尚有 ApprovalService 通知改动 — 合并时必须保留并重新验证通知事件，不能以候选覆盖共享工作文件。
