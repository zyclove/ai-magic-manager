# Android 临时访问原生存储验收计划

承接 `2ed6a73` 的前台宿主交付，补足 Android 新上下文、数据密钥与加密日志的真实进程恢复证据。复用 Flutter integration_test/drive、FlutterSecureStorage、Android 持久屏障、path_provider 和 Sembast，不改写密码算法或平台存储实现。

## 实施步骤

1. 独立测试签发者、服务地址与合成设备范围，运行时生成签名并只持久保存公钥和已签名文档。云响应为明确 MockClient 替代物，不连接实际服务器、不冒充成人批准。
2. 先用未写入状态的重放阶段做负控制；必须因缺失前置原生记录失败，不能因编译、安装或驱动失败充当 RED。
3. 分别构建并启动 write_pending、replay_pending、offline_expire_pause、verify_checking_reject、verify_blocked、apply_removal、verify_removed、cleanup。每步结束由宿主对照应用报告 PID 并确认该进程已死亡后才能进入下一步；不清数据、不卸载。
4. 检查原请求回执字节、截止时间、待核对状态、离线到期、CHECKING/BLOCKED 重开、撤回持久化以及文件/偏好中不存在已知明文载荷或数据密钥。
5. 每个进程检查既有身份、使用记录与基础配置文件摘要不变；清理只删除已经验证属于本夹具的一个文件和三个固定 SDK 键。
6. 恢复正常儿童端调试 APK，检查应用可启动，停止本任务模拟器；保存各阶段 APK/日志摘要、PID、结果与限制，再按用户授权阶段提交 dev。

## 关键判断

Ruling: 单条回执结果丢失仍可保存 VALID 上下文，但该请求需保留“待核对”及原回执 — SDK 将非致命传输失败表示为逐请求问题，并未完成服务确认 — 原生流程必须验证重放原请求后才清除问题，不能误要求整机 BLOCKED。

Ruling: 专用模拟器复用既有调试安装，不使用清数据或卸载获得干净结果 — 需要真实证明跨进程恢复与其他记录不被改写 — 首次写入若已有该合成范围则明确失败，必须分析残留而非自动清空。

Ruling: 本轮只证明受测 Android/API/插件组合的持久化行为 — 云授权、物理断电、硬件防回滚及系统管控是不同证据 — 与已有真实 Spring HTTP 结果组合报告，保持能力边界清楚。

## 执行中发现与调整

- 冷启动后该专用 AVD 没有调试应用。先完成访问缺失状态负控制，再复用已提交的身份/配置及使用情况原生夹具建立非空前置记录，避免将空值不变当作保护既有数据的证明。
- 首次访问 APK 启动发生引擎内核长度错误，尚未进入测试；设备安装摘要与构建包相同，内核组件边界有效，新旧包引擎/快照相同。停止预构建守护进程后，旧夹具及同一访问 APK 均实际进入预期缺失状态断言。未更改 APK 或清数据；初次启动失败不计 RED，也不宣称已定位其环境根因。
- Dart 运行时对内核长度有独立校验，不能用 ZIP/摘要校验替代实际启动；参考 [Dart 运行时 Reader 实现](https://dart.googlesource.com/sdk/+/refs/tags/3.2.0-46.0.dev/runtime/vm/kernel_binary.cc)。这里用于理解错误类别，不将旧源码或相似问题当作本次根因证据。
- 原集成驱动的请求超时不覆盖等待根 isolate；本轮专用驱动复用标准 `Future.timeout`，为完整连接与测试过程设置外层期限。进程是否停止仍由宿主核对。
- 首个写入测试实际通过，但 Flutter 控制台订阅漏掉了结果行，宿主因此拒绝计通过。Android 自身日志保留了该进程的完整结果。脚本改为读取当前存活 PID 的 Android 日志缓冲并严格核对唯一结果/阶段/PID；先继续原状态到精确清理，再从缺失状态负控制开始完整复跑，不通过重建记录掩盖回执状态。
