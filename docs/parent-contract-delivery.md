# 手机机构合同：核对、确认、恢复与当前权益

更新：2026-10-15。目标为中国大陆机构合同渠道。手机端接入已有的合同列表、机构投影、报价差异、历史、管理员确认及权益汇总接口，形成“服务方提交已签合同 → 独立审核 → 机构管理员核对确认 → 查看当前权益”的客户侧闭环。

## 操作流程

入口：“我的” → “商业账户” → **机构合同与确认**。机构所有者、机构管理员与审计员可进入；审计员仅查看。家庭、儿童、教师没有机构合同入口。服务端仍按真实角色、租户和近期认证校验请求。

1. **找到合同**：按合同编号查找已加载内容，支持游标分页。空目录提示联系机构采购负责人，由服务方提交和审核已签合同。
2. **核对服务事实**：展示合同编号、基础/加购名额、设备数量、功能、服务期和核验信息。价格、付款与责任以已签文件为准，手机页面没有支付扣款操作。
3. **核对当前报价**：读取绑定该合同版本的比较结果，说明报价版本、设备平台、设备模式、服务周期和差异原因。存在差异、报价尚未读取或合同不可确认时，确认按钮禁用。
4. **明确确认**：机构管理员通过底部按钮进入确认弹窗，再次核对机构、合同编号、数量与服务期。后台需要近期 MFA，发起人/独立审核人不能代替机构确认。
5. **查看当前权益**：确认后保留本机核对提醒，展示结果；完成核对后重新读取合同、报价、历史及机构权益汇总。当前付费权益与设备实际系统能力分别呈现。

页面支持 390×844 手机竖屏和两倍字体；详情、核验信息和确认说明均可滚动。列表和历史按接口游标分页，不静默截断。已处理的历史合同显示“合同已应用”，当前有效名额与功能以汇总接口为准，避免把过期、未来生效或后来撤销的历史记录当成当前授权。

## 恢复语义

现有确认 API 使用 `If-Match` 合同版本前置条件，接受成功后增加版本并写入状态。它没有“按原客户端请求编号查询提交回执”的能力，因此手机不能把当前 `APPLIED` 状态归因于某次请求或某个管理员。

| 情况 | 产品行为 |
|---|---|
| 确认回复成功 | 展示服务端返回的最新合同状态，并读取当前权益 |
| 回复丢失或网络错误 | 保存待核对记录；用户显式查询当前合同，不自动重发确认 |
| 当前仍待确认 | 清除提醒前说明会重新读取和核对；必须再次查看最新合同与报价并确认 |
| 当前已应用/驳回 | 说明当前状态，完成核对后刷新目录与详情；不重复应用 |
| 当前无权读取 | 保留待核对记录，提示权限错误；恢复不会绕过授权 |
| 安全存储失败 | 不发送确认；重新读取本机记录后才允许下一次操作 |
| 账号、角色或机构改变 | 关闭旧详情，旧请求不能向新机构展示结果 |

本机安全存储只保存 `reviewId` 和确认前 `version`，按操作者和租户隔离；不存合同编号、采购方信息、签署材料、证据令牌或密钥。存储读取拒绝额外字段及异常长度。失去前台会隐藏页面、关闭确认弹窗，使等待存储或令牌刷新的写操作失效。重新打开页面只加载本机提醒，不自动发送确认。

## 接口与权限

复用 `/api/v1/tenants/{tenantId}/contracts`：

| 路径 | 行为与校验 |
|---|---|
| `GET /contracts?limit=50&cursor=...` | 机构合同目录；客户端逐条检查租户与协议 |
| `GET /contracts/{id}` | 机构投影；不含平台提交人、审核人或接受人身份 |
| `GET /contracts/{id}/comparison` | 必须与当前合同 ID、版本、报价 ID 和合同报价版本一致 |
| `GET /contracts/{id}/history?limit=50&beforeVersion=...` | 版本倒序分页；机构历史不含内部原因、操作者或关联请求编号 |
| `POST /contracts/{id}/accept` | `If-Match`、OWNER/ORG_ADMIN、近期 MFA、独立性、有效合同和当前报价检查；同事务应用权益并写历史/审计 |
| `GET /commercial-entitlements` | 当前有效权益汇总；设备可执行能力另行核对 |

合同确认接口沿用既有版本前置条件和事务约束。已有平台目录/合同独立审核、来源签名验证、暂停开通开关与撤销处理继续由后端负责。本阶段不在客户端写入任何商业授权，也不改变生产发布开关。

## 共用组件与分层

新增内部纯 Dart 包 **`packages/commerce_contracts`**，从管理台现有模型提取，供手机与管理台共同使用：

- 合同状态、机构/平台投影、报价差异、处理历史、能力声明。
- 商业渠道、平台、设备模式、计费周期、名额与功能词汇。
- 安全整数、可展示日期、枚举、重复记录和历史顺序检查。
- `ContractProtocolException` 由两端仓储分别适配成各自的 `INVALID_CONTRACT_RESPONSE` 传输错误。

管理台原 `core/contracts.dart` 保留导出入口；`commercial_catalog.dart` 复用共用词汇；仓储负责错误适配。手机 `core/contracts.dart` 负责 HTTP、恢复记录和确认状态机，`ui/contracts_center.dart` 负责交互。

商业账户卡片同时补齐身份隔离：其状态按操作者、机构、角色与登录代次重新创建；失去前台隐藏，恢复时重新读取。前一机构迟到响应不会覆盖当前机构名额。账户汇总的核算时间也增加可展示日期边界检查。

两端只增加一个本地路径依赖，无新的第三方网络服务或运行时 SDK。打包时需要包含 `packages/commerce_contracts`，正常执行 Flutter 依赖解析即可。

## 验证与交付边界

最终独立副本结果：**手机 73 项联合回归、管理台 19 项商业回归、后端 14 项检查全部通过，无后端跳过**。手机 13 项合同专项包含在 73 项之中；后端包含真实手机 HTTP 联调。

- 手机新增 13 项检查：协议与日期边界、跨租户与版本绑定、回复丢失后的只读恢复、重新核对、报价差异、存储失败、前台/令牌刷新保护、存储隔离、1×/2× 字体、审计员只读、后台弹窗与切换机构，以及商业账户迟到响应隔离。
- 管理台 19 项商业功能回归覆盖合同、认证恢复、目录编辑和权益显示。
- 后端 14 项检查覆盖合同签署来源验证、独立审核、机构确认、暂停开通规则及真实手机 HTTP 联调。
- 真实联调使用生产手机仓储、共享模型和确认控制器：读取已独立审核合同/报价/历史，提交确认后主动丢弃成功回复，重建控制器并查询当前合同，读取 25 台设备权益；确认没有重复 POST、权益来源或确认事件。
- 本地实际界面图：`.local/parent-contract-portrait.png`。延续现有 Material 风格，依据实际渲染和交互检查迭代。
- 以已提交基线 `d226f38` 加本阶段文件构建独立副本；父母端依赖变更只纳入本地合同包，保留并行任务的扫码依赖与首用流程。

H2 MySQL 模式、JWT/MFA、合同签署来源验证器与手机安全存储在联调中使用显式夹具。结果不代表真实签署服务、真实机构合同、MySQL/OceanBase、Android 实机安全存储或正式商业上线已验收。本阶段未替换共享 18101 服务，也未生成正式安装包。
