## State and dispatch changes

- `uncertain` becomes a Map from request ID to that operation's monotonically allocated `ackSequence`. Failure records the sequence of the actual dispatched operation. Every existing UI/guard membership lookup uses containsKey; existing labels and explanatory text are preserved.
- Fresh read start takes an independent copy of the then-current uncertainty map. Only a current + generation + filter-matching fresh success removes entries whose current operation sequence still equals its captured sequence. New or changed uncertainty is retained. Append success/error does not reconcile uncertainty. No whole-map clear remains.
- `lastDispatchedSequence` retains each ID's most recent dispatch across fresh/append reads. Opening a confirmation captures that ID's current value. After confirmAction returns, current, sending, uncertainty and that same captured per-ID value are rechecked before allocating the next global sequence and synchronously registering sending/dispatch. Cancellation changes no sequence. A dispatch on another ID does not invalidate this ID's confirmation.
- The same scope-bound POST, item.version, response ID/state validation and successful acknowledgement's necessary fresh reload are preserved. No global busy guard discards that reload. FirstPageLoaded continues to describe only a valid first-page read; it cannot by itself unlock an uncertain acknowledgement.

## Three required ordering traces — UNRUN

1. **Read B starts while acknowledgement A is pending.** A is not yet in uncertain, so B's snapshot cannot contain A's later operation. A's 503/network failure records its sequence. B's later old OPEN response may populate the list, but cannot remove that newly added uncertainty; the row remains locked for explicit later reconciliation.
2. **Read C starts after A fails.** C captures A's uncertainty sequence. A matching current fresh success may remove that same unchanged entry. If the current entry has changed to a different operation, C cannot remove it. Append reads never perform this removal.
3. **Two old confirmation windows for the same ID.** Both capture the earlier per-ID dispatch value. The first accepted completion registers a new value before its request await. The other old completion is rejected while the first is pending, after failure, and after success plus its fresh reload, because the per-ID dispatch value changed even when sending/uncertain no longer contains the ID. A newly opened confirmation can capture the latest value; an unrelated ID remains independent.

These are source-order statements, not an executed predicate model or runtime verification.
