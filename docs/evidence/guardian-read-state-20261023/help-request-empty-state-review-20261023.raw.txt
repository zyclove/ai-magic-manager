# 求助记录读取失败与成功空态：静态审查

## 基线与结论

审查日期：2026-10-23。只读本地 `dev` 基线为 `979b02ce251d9ea9c0a3ba7a85d44fdf59d53e48`。本轮发现一项 **P2**：仍挂载的求助页面在首屏读取失败后，同时显示错误和“暂无待查看求助 / 暂无求助记录”。这是当前实现中的现存问题；本次分页补丁没有引入该分支。

本报告仅依据源码控制流，未执行应用、测试、SDK、编译或界面渲染。本轮仅新增该审查文档，没有修改生产代码、测试代码或服务，没有执行 Git 写操作。发现已按现有分工发给主任务处理。

## 触发路径

1. 当前账号和工作空间保持有效，打开求助记录，或执行显式刷新、切换筛选。
2. `HelpRequestsPage.load(more: false)` 在发请求前将 `requests` 清空、`cursor` 清空并设置 `loading = true`（[源码](../../apps/guardian/lib/pages/help_requests_page.dart#L59)，基线 69–74 行）。
3. 首屏 GET 返回普通 503，或产生 `NETWORK_ERROR`。catch 设置 `error`，finally 设置 `loading = false`，尚未取得任何成功的当前筛选结果（基线 89–107 行）。
4. build 的错误区域显示失败和重试（基线 193–203 行），下方 Panel 又仅凭 `requests.isEmpty` 显示成功空态（基线 210–212 行）。

`Api.page` 通过 `Api.send` 读取；HTTP 错误会抛出 `ApiFailure`，超时和客户端传输错误会转成 `NETWORK_ERROR`（[接口实现](../../apps/guardian/lib/core/api.dart#L300)，基线 300–338 行）。上述路径无需权限变化、非法游标或服务端数据删除。

## 影响与修复要求

错误和“暂无求助”的结论同时出现，可能误导监护人或值班人员的跟进判断。服务端记录是否存在仍然未知；本发现没有证明业务记录丢失或实际漏处理事件。

空态应由**当前筛选的首屏成功读取且结果确为空**驱动。首屏读取失败应显示读取未完成、重试和适用的重新验证入口。读取状态需要与确认操作结果未定、追加分页错误分别维护；当前全局 `error` 同时承载读取与确认错误，不能把它直接当作成功读取标志。

现有请求代次、筛选、权限与工作空间检查需要保留，以免迟到响应使新筛选出现旧空态。

## 后续验收场景（尚未运行）

- 页面仍挂载：首次 503、传输失败、显式刷新失败、筛选读取失败均不得显示成功空态。
- 同一筛选重试成功返回空页后，才显示对应空态；成功返回记录时显示记录并清除读取失败。
- 切换筛选或工作空间后，旧请求成功或失败不得改写当前读取状态。
- 确认结果未定、确认后的刷新失败、追加分页失败分别保留各自恢复语义。

现有 `approval_help_flow_browser_test.dart` 中初始读取 error 用例会先移除页面（基线 267–280 行），没有覆盖“仍挂载的读取失败不得显示成功空态”。`managed_android_review_recovery_test.dart` 已有同类状态区分的场景描述，可作为后续测试组织参考；本轮未执行该测试，也未假定其结果适用于求助页面。
