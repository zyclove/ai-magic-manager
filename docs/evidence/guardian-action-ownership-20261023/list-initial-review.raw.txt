## F1 / P2：审计旧重试把旧游标配上新筛选，并取得新的请求代次

主位置：`apps/guardian/lib/ui/audit_view.dart:106`；数据流证据：77–110、203–209、293–310、352–362。Repository：`apps/guardian/lib/core/audit.dart:28–39`。后端实际限制：`backend/src/main/java/com/aimanager/tenant/internal/AuditExplorer.java:54–76`。

1. 筛选 A 的下一页失败后，106 行将 destination/direction 捕进 retry，但没有捕获并校验失败时的 generation/repository；94 行实际读取的是可变字段 applied。
2. 用户应用筛选 B，80–85 行更换 applied 并清 history/cursor；旧 FailureView 虽被移除，已持有或已排队的旧重试闭包本身仍可被投递。
3. 旧重试随后调用 load，79 行主动增加 generation，87–92 行清除当前 B 的 page/error/retry，再用 **B 的 applied + A 的 destination** 发 GET。它没有被 busy/opening 或期望代次挡住；甚至可使较早发出的正确 B 响应因 ticket 不匹配而被忽略。
4. 这不是跨租户越权：后端将 tenant+selection 指纹写入 cursor，65–76 行明确拒绝与新 selection 不一致的旧 cursor，产生 INVALID_CURSOR。可静态证明的用户影响是新筛选结果被旧控件打断并进入错误状态；未声称后端返回错误数据。

同根因还影响分页闭包：355/361 行在调用时读取当前 history/page，只有构建时 disabled，没有实时票据与忙碌校验。旧 next 在另一次 load 已把 page 清为 null 后仍可能访问 page!。这是 F1 的同一事件入口问题，不另立发现。

### 最小合理设计

- 保持当前 query/API、cursor 栈及方向语义，使用现成 State/Material，不引入依赖。
- 当前性包含 mounted、同一个 repository 及 repository.current()。构建事件捕获 repository+generation，在任何表单清空、日期变更、分页栈变更、导出/详情或读取前实时检查票据和 busy/opening。
- next/previous 在构建时捕获不可变目标 cursor，不通过旧回调临时解引用当前 page/history。
- 失败 retry 捕获当次 repository、generation、destination、direction，只在仍为同一代次且空闲时执行原请求。新筛选/翻页后，旧 retry 不清数据、不递增代次、不发读。
- load 的入口先校验当前 scope；初始化、明确新读取和内部必要调用仍正常。详情 GET/错误和日期选择器 await 返回均检查原 owner+ticket；旧完成不能污染新列表。若新读取允许替代详情请求，opening 锁也须有归属，不能由旧 finally 解锁新详情或永久锁住新列表。
- 覆盖路由不在本次扩展范围；保留授权失效隐藏规则、导出契约及必要刷新。
