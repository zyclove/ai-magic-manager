## Lifetime and recovery reasoning (static only)

- A valid first dispatch checks its old page ticket before calling load/read. Those existing methods synchronously increment generation before their network awaits. The first event is therefore admitted, and another handler retained from the same old build is rejected afterward; the event is not checked against its own incremented generation.
- The existing `load` and `read` operation bodies, current/generation result gates, activeRead ownership/finally, and successful write/open follow-up `await load(owner: repository)` are retained. No generic busy guard was added to internal load: the read operation may legitimately perform its required refresh while activeRead still owns the operation.
- After a failure settles, its ticket is still current and the outer finally releases busy/activeRead; the error action may retry the captured exact IDs/requestId. On retry dispatch the existing read/load increments generation, making that same old retry closure inert. A later success/filter/page/refresh also increments generation and makes obsolete error closures inert.
- For an access-status failure, the original snapshot concealment and retry-as-load behavior are retained. The candidate does not turn this recovery into a repeated write.
- Same repository identity alone is not accepted as current-page ownership. No snapshot-null heuristic or substitution of new current IDs is introduced.
- Widget labels, notification copy, Material controls, repository protocol/endpoints/body, bulk limit, unread count behavior and ordinary successful filter/page semantics are unchanged. No new state framework or dependency is introduced.
- An error generated by a repeated cursor keeps its page ticket until its explicit first-page retry begins. That retry is guarded before changing cursors and then takes the normal load generation.

## Necessary future scenarios (all UNRUN)

- Retain page batch, single read and open-current-request callbacks; complete a same-owner filter/next-page/refresh load; invoke old callbacks and assert no writes, onOpen, cursor changes or new reads.
- Retain previous on page two; return to the first page and complete it; invoke old previous and assert the current cursor stack is intact and no exception/request occurs. Exercise old next/home/filter/refresh the same way.
- Invoke a current event twice before a pump; first dispatch happens once and the second is inert. Keep current same-page batch/single/open success paths normal.
- A failed current read retries exactly its original IDs/requestId once, including repeated held retry calls. After a later successful refresh or newer failure, both the old displayed error callback and the old stored retry closure are inert.
- A failed load retries its current failed cursor/filter, then becomes inert after another generation; 401/403 recovery remains read-only.
- Read success performs the necessary internal load while activeRead is still set; ensure no permanent busy state, lost refresh or self-invalidating first dispatch.
- Existing owner loss/disposal, late responses, original-ID retry, pending duplicate prevention and notification-to-request navigation tests remain relevant. None was run for this candidate, and old passes do not cover it.
