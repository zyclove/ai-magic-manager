## Lifecycle review

### Covered parent close is inert and does not poison later close

`after.dart:100-106` checks mounted, closeRequested and writeBusy, then obtains ModalRoute and rejects null, non-current or inactive routes before setting closeRequested. An ordinary device subflow makes the parent route non-current. Its held close therefore cannot reach the host callback, and the close latch stays false. When the cover has legitimately finished, the same parent route can again pass current/active and close normally.

The production callback remains `Navigator.of(dialogContext).pop()` (`apps/guardian/lib/pages/console_pages.dart:1022-1029`). The checked State context belongs to DeviceManagementDialog built in that same dialog route. There is no await between the route guard and this fixed immediate host callback. The narrow fix therefore blocks the reported stale parent handler from popping the then-current covering route.

### First accepted close locks before invoking the host

`after.dart:104` sets closeRequested synchronously before `widget.onClose()` at 105. A second held callback in the same turn returns at line 101 even before a reverse transition/dispose. After disposal mounted is false. If another mechanism already popped the original route, the active/current check rejects its held callback. The latch also avoids relying solely on a later route-status update.

The latch is not cleared when a cover is dismissed because the rejected covered branch never set it. Its lack of setState is sufficient for this action-entry guard in the fixed production immediate-close host; no visual success state is claimed or required.

### Read cancellation and safe exit after scope loss are preserved

The guard uses writeBusy, not the general controller busy or hasAccess. `core/device_management.dart:587-615` sets only busy for ordinary subflows; `:508-526` does so for reads. A plain read therefore remains closeable when the originating route is current. Actual writes still use writeBusy and remain protected. Scope invalidation hides private fields and clears writeBusy in the existing controller (`:437-448`); this close entry does not require access to the old data, so the current redacted window retains its close action.

The candidate changes no controller/API, access/version/key behavior, host callback, subflow action, confirmation lifetime, current action busy lock or field rendering. It does not claim support for an arbitrary onClose implementation that fails to complete its window, nor for reusing the same State as an unrelated new route via GlobalKey.
