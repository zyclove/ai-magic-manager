## 问题和修改

1. 订单请求结果未知时，支付协调器已持久保存原请求编号、套餐和报价版本，但尚无订单编号。会员页原先将“核对原订单请求”与新购买共同受销售开关限制，闭售时无法恢复这一原请求。现在按钮与处理入口共用 `canRequestOrder`：只允许原套餐的持久请求继续核对；无原请求的新购买仍要求会员与报价的支付开关均开放。协调器继续使用保存的原编号与原报价版本，不替换请求或自动采用新价格。
2. “我的订单”原先创建另一份支付协调器。详情页确认终态并清除持久待办后，会员页原实例仍保留旧内存提示。现在此入口与新建订单、待核对入口一样，向详情页传入会员页的同一协调器，使已完成核对的状态可直接反映到返回后的会员页。

统一入口继续检查当前身份、角色、前台状态、页面与协调器忙碌状态、持久记录已读取及是否已有待核对订单。已有订单仍须先核对，不允许在不同套餐下重建原请求。未改变支付 SDK 派发、服务端收费门禁、退款或成员权限。

本次没有因持久记录意外缺失而自动清除内存，也没有放宽未知请求的防重保护。后端原编号恢复返回既有订单的约束继续适用；如原请求尚未落库，由服务端按原编号和原请求内容处理。
