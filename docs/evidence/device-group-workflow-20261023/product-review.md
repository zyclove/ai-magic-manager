# 设备组批量选择流程独立源码审阅

## 范围与结论

- 基线：`91cffeeab202414a451100dd48511fc78066692e`，本次只读 Main 与现有测试，只在此 `.cache` 目录写审阅记录。
- 未运行 SDK、测试、编译、浏览器、网络或 API；下列结论是代码证据与可推导路径，不是运行复现或验收通过。
- 最有价值的改进是让机构管理员能在跨页选择后快速复核完整清单，并让成员分页失败可原位恢复。无需更改 API、增加依赖或扩张单次 50 台上限。

## 真实缺口与最小方案

### F1 / P2：跨页选择后缺少完整复核入口，50 台逐项纠错成本高

证据：

- `apps/guardian/lib/ui/device_group_batch_picker.dart:30–37` 只保存 `selected`、已加载 `devices` 和分页游标，没有搜索或仅看已选状态。
- `:189–200` 已支持跨页累积选择且运行时严格限制 50 台；`:226–265` 仅显示总数与全部已加载设备的 `ListView`。
- `:257–260` 行内显示名称、平台、状态和设备 ID；没有完整已选视图。第二页选错后，管理员只能在累积列表中逐条找回。
- `apps/guardian/lib/pages/device_groups_page.dart:379–384` 与 `:409–414` 的后续确认只展示前三个名称加“等”和总数，不能替代完整清单复核。

最小方案：

1. 在现有批量选择器内加入搜索（名称、设备 ID、注册 ID）与“仅看已选”；搜索明确标为“搜索已加载设备”，显示“已加载 X 台，还有更多设备”或“全部已加载”，不能把局部结果表达为整个机构搜索结果。
2. 已选过滤从整个 `selected`/已加载列表派生，跨页选择不因筛选、清除搜索或加载失败而丢失；“清空选择”只影响草稿，不发请求。
3. 如提供“选择当前筛选结果”，只加入已加载且可选的明确集合；在点击时重新计算与现有选择的并集，超过 50 时禁用并说明，不能悄悄截取前 50、自动翻页或隐式全机构全选。
4. 加载更多操作独立于筛选后的列表尾部，避免搜索无匹配时把后续页入口隐藏。仅看已选时仍可明确切回所有已加载设备继续选择。
5. 保留当前“核对并加入/移出 N 台”与第二层固定请求确认；可以在下一阶段把确认说明升级为可展开的完整固定清单。当前阶段先让选择器本身可完整复核，避免重做提交协议。

工作示例参考：现有 `apps/guardian/lib/ui/usage_report_device_picker.dart:146–179`、`:198–275` 已实现本地搜索、仅看已选、清空与点击时复查上限。可沿用 Flutter Material 原生控件和同项目交互原则，但批量分组选择器是分页数据，不能直接复制“全量 targets”措辞或加载逻辑。

### F2 / P2：组内成员下一页成功恢复后，旧错误仍留在页面且“重试”会重载第一页

根因链：

- `apps/guardian/lib/pages/device_groups_page.dart:236–257`：`moreMembers()` 在失败时把异常写入全局 `error`（`:253–254`）。
- 下一次点击“加载更多设备”时只设置 `loadingMore=true`（`:240`）；成功分支只追加 `members` 并更新游标（`:249–252`），不清除 `error`。
- 因此一次分页失败后，再加载同一游标成功，页面 `:593–597` 仍持续展示原失败；该错误块的“重试”调用 `open(selectedId!)`。
- `open()` 的 `:196–204` 清空全部已加载成员和游标、重发三项初始读取。管理员已经浏览的多页会被回到第一页，不能通过错误块原位恢复。
- `moreMembers()` 本身保留原 `nextMemberCursor` 和 `members`，所以原位重试已有数据基础。

最小方案：

1. 区分首屏/详情读取错误与成员分页错误，例如 `error` 与 `memberPageError`；首屏重试继续调用 `open()`。
2. 把分页错误与“重试加载更多”放在组内列表底部，重试调用原 `moreMembers()`，保持 `members`、`nextMemberCursor`、`memberFilter`。
3. 新一次分页开始或成功时清除分页错误；切组、切状态、刷新、失权时清除分页错误，并复用现有 scope/generation 防止旧结果写入新视图。
4. 原子读取失败仍不展示半成品 `detail/summary`，不要为了分页恢复削弱现有 `open()` 三项一致性校验。

注：批量选择器自身没有同一残留错误问题。其 `load()` 的 `:149–152` 会清旧错误，`:173–176` 成功才追加列表/更新 cursor，`:230–231` 重试根据保留的 cursor 继续当前失败页。

## 已确认存在、应保留的边界

- 单次显式 50 台：picker `:189–200` 的点击时检查与 `:253–255` 的展示禁用配合；不是仅靠禁用按钮。
- 选择目标绑定注册：picker `:162–170` 校验行与跨页重复 ID，`:192–193` 检查该设备/注册组合仍属于已加载项。页面批量请求 `:388–390`、`:418–421` 带每台 `deviceId/registrationId`、捕获组 `version` 与一个固定 `key`。
- 服务端边界：`backend/src/main/java/com/aimanager/fleet/internal/DeviceGroupService.java:357–439`、`:443–505` 的事务、50 台/唯一设备检查、组版本检查、注册/状态/成员校验和“全部校验后才写入”是权威边界；UI 改善不能替代或放松它们。
- 工作空间/权限失效：页面 `:45–48` 与 `:88–92` 捕获 session/scope/generation；`:51–85` 隐藏数据并结束自有对话框。picker `:39–68` 单向失效、`:204–210` 隐藏原选择并给关闭入口。没有发现此次审阅范围内必须通过修改 API 解决的失权路径。
- 路由覆盖：picker `:48–51` 不允许覆盖时进行选择/确认，`OwnedDialogRoute.finish()` 只结束自身；不能把普通 `Navigator.pop` 用于关闭已被其他对话框覆盖的旧路由。
- 取消：正常取消仅退出草稿；失权分支具有独立关闭动作。覆盖时保留回调不应操作顶层路由。这与“取消不受业务权限阻挡”的意图不冲突，不把不可见底层按钮的禁用当真实用户困死。
- 页面确认 `:747–937` 固定操作/幂等 key，提交锁与不确定结果原请求重试；412 禁止继续提交并引导关闭刷新。此次改善不应让用户不确定重试时改选设备或换 key。

## 现有测试边界与待执行验收

源码搜索发现 `apps/guardian/test/submit_direct_variant_test.dart:244–273` 覆盖设备组归档确认的单次提交、If-Match 与 Idempotency-Key；没有在 `apps/guardian/test` 内发现直接构造 `DeviceGroupBatchPicker` 的专门测试。策略目标选择相关测试读取设备组，但不能据此声称批量选择 UI 已覆盖。

资源窗口恢复后需要的新验收范围（此处未准备/运行测试）：

1. 两页各 50 个候选，跨页选中后，搜索/清除/仅看已选仍能完整复核并取消任意已选；选择计数和最终显式 body 一致。
2. 停用设备不得加入；移出模式允许历史/失效成员但保留原 registration；旧回调不得越过 50。
3. 搜索零匹配但有下一页时，加载更多入口仍存在；明确表述局部搜索范围。
4. 第二页失败后原位重试同一 cursor，成员与选择不清空、不重复；成功后旧错误消失。
5. 组成员列表第一页成功、下一页失败再成功，错误只在分页区展示，已加载项和状态筛选不重置。
6. 选择/加载/确认等待期间，session 失权、换机构、ABA、父路由离开或其他路由覆盖，旧回调不得发请求或误关其他路由。
7. 批量确认保持同组版本、相同设备/注册固定清单和同一幂等 key；412、409 注册变化、503/不确定重试均保留既有原子与恢复含义。
