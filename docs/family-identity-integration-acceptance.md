## 隔离 MySQL 验收方法

入口为 [`scripts/test_family_identity_mysql.ps1`](../scripts/test_family_identity_mysql.ps1)，可按 `Start → Verify → Cleanup` 恢复执行。新运行默认在仓库忽略的 `.cache/` 下，兼容既有 `.local/` 记录；拒绝路径及目录链接穿透，清理前核对本轮资源身份与标签。

先从待验收源码构建身份扩展，再用 `-ProviderJar` 指定该产物并记录摘要。已有 `target/` 或部署目录中的旧 JAR 不会因源码修改自动更新，不能据此宣称修复已生效。本轮使用独立冻结副本的新构建，不覆盖旧部署产物。

环境为全新 MySQL 8.4.11、Keycloak 26.8.0、内部隔离网络，无宿主端口、无持久卷。数据库使用临时存储，Keycloak 为单节点、本地缓存。生产扩展与测试夹具分别校验并打包，真实数据库和 OIDC／PKCE 与模拟供应商分别记录。测试使用专属临时证书的 HTTPS，只给本轮 Java 进程信任该证书，保留主机名检查及生成身份域的 SSL 策略，不写全局信任库。

验证目标包括 RR 当前读取、行锁等待及回滚释放、手机号与微信并发唯一归属、身份版本不回退、原用户不变、四种账号操作，以及旧在线／离线会话失效。签发令牌采用严格 JSON 重复字段检查，不能以单元测试代替实际签发。

最终实际运行 21 项全部通过。用户读取修复核对 Keycloak 26.8 的全部 14 个用户基础字段；微信读取修复采用独立当前投影，避免再次通过实体 `refresh` 读回旧快照。实际检查证明：变更前已经持有的原用户模型仍可正常使用，原用户及其他用户的待提交改动在下一次 HTTP 请求仍然存在。没有采用清空持久化上下文或替换原用户的方式。此实现依赖已核验版本的表结构，升级 Keycloak 后必须重新执行对应回归与 MySQL 验收。

单节点结果不能证明多节点缓存失效；短信夹具只替换发送，微信夹具只替换供应商交换。测试手机号为虚构号码，不发送短信、不保存真实手机号、验证码、授权码或令牌。

验收完成已按专属标签清理本轮两个容器和网络，未触及已有服务。运行回执、源码及客户端摘要、生产 JAR 与夹具隔离清单保留在 `.cache/family-identity-20261017/mysql-full-14/`，清理摘要在 `mysql-tools/out/`。
